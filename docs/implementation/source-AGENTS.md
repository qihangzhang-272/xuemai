# AGENTS.md — 学脉 Codex 开发护栏

## 1. 项目定位

学脉是面向中国小学到高中学科类教培老师的微信式 AI 教学工作台。

产品基本隐喻：

- 学生是联系人。
- 班级是群聊。
- 聊天是老师记录、提问、上传学生材料的入口。
- Skill 是确定性教学工作流。
- SkillCard 是正式 AI 输出节点。
- 老师确认入档，才形成学生长期档案价值。

产品本体：

- 学生是持续存在的服务主体，新生、在读、暂停、结束只是阶段变化。
- 家长、班级、老师、机构成员和服务周期是围绕学生形成的关系。
- 课堂、材料、反馈、沟通、跟进和服务变化是按时间发生的事件。
- 学生材料和已确认记录是证据；AI 分析是草稿结论；老师确认后才成为正式结果。
- 待反馈、待回复、待跟进和交接是尚未完成的责任，不是独立业务系统。
- 总览、月报、报告、续费准备和批量管理是对同一批学生、关系、事件、证据和责任的不同视图或操作方式。

学脉不是：

- 纯聊天机器人。
- 普通 AI 工具箱。
- 老师备课工具。
- 学生自学工具。
- 复杂多 Agent 实验平台。
- 教务后台或表单系统。

当前核心产品逻辑：

```text
聊天是入口
Skill 是执行
卡片是结果节点
分析详情页是完整反馈报告
确认入档才形成长期学生档案
```

产品讨论与 PRD 默认只表达产品形态：用户、场景、页面、流程、功能、状态、版本、价值和范围边界。除非用户明确要求技术方案，否则不要展开 API、Webhook、Token、签名、幂等、数据库、架构、部署等实现细节。

## 2. 当前用户与材料边界

目标用户：

- 中国小学学科类教培老师。
- 中国初中学科类教培老师。
- 中国高中学科类教培老师。
- 一对一老师。
- 小班课老师。
- 教培机构授课老师。
- 个体老师。

当前重点分析对象：

- 学生试卷。
- 学生作业照片。
- 错题照片。
- 错题本。
- 学生笔记。
- 练习记录。
- 老师批改后的学生材料。
- 阶段测验、单元测验、周测、月考材料。
- 老师粘贴的学生答案或错题内容。

不分析对象：

- 老师 PPT。
- 老师教案。
- 老师备课资料。
- 纯教材内容。
- 空白试卷模板。
- 泛泛教学资料。
- 大学、成人教育、职业教育材料。

硬规则：

```text
没有学生作答、订正、批改、笔记或练习痕迹，就不能推断学生能力、薄弱点、错因或学习状态。
```

## 3. 当前开发范式

当前采用：

```text
Workflow-first Agent Shell + Harness-first AI Coding
```

开发原则：

- 一个 API Call 能解决的，不做 Agent。
- 固定流程任务，做 Workflow。
- 只有需要多轮参与、上下文持续变化或按钮爆炸时，才考虑 Agent Shell。
- 当前不要做复杂多 Agent。
- 当前不要引入 LangGraph、Redis、向量库、MCP、A2A，除非任务明确要求。
- Prompt 从短版本开始，基于失败案例迭代。
- 每个 Skill 只加载必要上下文。

## 4. 当前阶段目标

优先打通 MVP 闭环：

```text
学生/班级会话
→ 老师记录课堂内容或上传学生学习材料
→ Skill 生成学习记录卡片 / 学情分析卡片
→ 会话页输出微信反馈卡片
→ 老师复制 / 编辑 / 标记已发
→ 反馈状态更新为待反馈 / 已反馈
→ 老师确认入档
→ 学生时间线沉淀
→ 学情报告和月报复用

注意：反馈状态优先级高于入档状态。用户界面优先显示待反馈 / 已反馈，再显示待入档 / 已入档。
```

不要把所有功能塞进学生详情页。学生详情页只看状态；会话页才是入口；分析详情页看完整报告。

### 4.1 产品版本边界

产品只设置两个正式版本：

```text
个人版
机构版
```

- 不单独设置工作室版；只有单一数据所有者、单账号使用的工作室归入个人版，需要多账号、多人协作或角色权限的工作室归入机构版。
- 当前不做集团版；多层级总部管控、复杂多校区组织、集团级数据驾驶舱、SSO、私有化和深度定制集成不进入当前范围。
- 后续客户分类、功能规划、定价和 PRD 均按个人版与机构版两套账户模型展开，避免衍生额外产品版本。

### 4.2 工作台与批量操作边界

- 产品应在工作台提供个人总览、机构总览、异常、提醒和待处理责任；每个数字或异常都应能进入具体清单处理。
- 批量操作通过学生、班级、工作台清单或管理页的多选模式完成，不作为独立一级业务入口；可用于学生分班、负责人分配、服务状态、反馈/月报草稿、普通跟进和交接，但个性化结果必须按学生独立保留。
- 批量生成不等于批量确认；未逐项检查的个性化反馈不得直接批量发送，学生长期档案不得一键批量确认，高风险家长事项不得普通批量关闭。

## 5. 页面分级与职责

### 5.1 一级页面

```text
工作台
会话
学生
班级
管理
```

- 工作台合并整体状态、异常、提醒和待处理责任。
- 会话是课堂记录、材料上传、家长消息和结果卡片的高频入口。
- 学生页按咨询、测评、正式服务、暂停、结束等生命周期状态查看同一学生主体。
- 班级页承载群体教学关系、公共课堂记录和逐学生独立反馈。
- 管理页承载成员角色、分配交接、批量操作、数据来源和个人/机构设置。
- 批量管理不是独立一级业务页面，而是对象列表和管理页中的操作模式；批量结果可进入二级详情。

### 5.2 二级详情页

```text
分析详情页
学情报告详情页
月报详情页
历史反馈详情页
历史沟通详情页
新生测评详情页
批量结果详情页
数据接入详情页
```

统一命名规则：

- 不再使用“审核页”作为页面名。
- 原“审核页 / 证据详情页 / 分析详情页”统一叫“分析详情页”。
- 内部可以有“待反馈、已反馈、待入档、已入档、需补充、证据不足”等状态，但页面名不叫审核页。

### 5.3 卡片层

```text
SkillCard
学习记录卡片
学情分析卡片
微信反馈卡片
错题分析卡片
月报草稿卡
课堂反馈卡
```

### 5.4 弹窗 / 抽屉层

```text
编辑微信反馈
查看来源
风险提示
确认入档
查看原始材料
```

## 6. 关键页面规则

### 6.1 会话页

会话页是主工作入口。

老师在会话页：

- 记录课堂内容。
- 上传学生学习材料。
- 输入补充要求。
- 接收 SkillCard。
- 查看微信反馈卡片。
- 复制、编辑、标记已发。
- 点击“查看详情”打开分析详情页。

会话页不要展示完整长报告。

### 6.2 学生详情页

学生详情页是学生学情状态页。

只展示：

- 学生基础信息。
- 当前学习状态。
- 近期关注点。
- 高频薄弱点。
- 最近学习记录。
- 学情时间线。
- 最近反馈状态。
- AI 学情建议。

学生详情页不要堆：

- 上传材料。
- 去审核。
- 确认入档。
- 逐题分析。
- 大量任务按钮。
- 复杂工作台操作。

学生详情页中的“查看详情”统一打开分析详情页或学情报告详情页。

### 6.3 分析详情页 / 学情报告详情页

分析详情页展示一次学生学习材料分析后的完整反馈报告。

页面重点是反馈，不是任务。

应包含：

- 报告基本信息。
- 状态：待反馈 / 已反馈 / 待入档 / 已入档 / 证据不足 / 需补充材料。
- 常规显示优先级：已反馈 > 待反馈 > 已入档 > 待入档。
- 如果同时存在反馈状态和入档状态，主状态显示反馈，入档状态作为次级标记。
- 核心概览。
- 结论总览。
- 数据可信度。
- 学情传导图。
- 能力维度反馈。
- 错误模式反馈。
- 知识薄弱点反馈。
- 难度层表现反馈。
- 学习策略表现反馈。
- 学科能力反馈。
- 重点错题成因反馈。
- 优先关注点反馈。
- 表现空间反馈。
- 复发风险反馈。
- 近期巩固方向。
- 家长微信反馈。
- 反馈状态和入档状态。
- 来源与注意事项。

不要在分析详情页加入任务化模块，例如：

- 7 天打卡计划。
- 每日任务。
- D1 / D2 / D3 执行表。
- 完成任务按钮。
- 生成教案。
- 自动派发任务。

分析详情页可以有“确认入档”，但不要做成任务中心。

### 6.4 微信反馈卡片

微信反馈卡片只作为会话页中的 AI 输出卡片出现。

卡片包含：

- 微信反馈正文。
- 复制。
- 编辑。
- 标记已发。
- 查看详情。

微信反馈卡片状态：

```text
待反馈
已反馈
```

规则：只要报告存在待处理反馈或已发送反馈，列表和卡片主状态优先显示反馈状态；入档状态只作为次级信息。

点击“查看详情”：

- PC 端在右侧打开分析详情页。
- 移动端跳转到分析详情页。

微信可通过官方或已确认合规的授权渠道直接接入。老师可在学脉中接收家长消息，并在检查最终版本后主动点击发送；AI 不得静默自动外发，未绑定或授权失效时保留复制与手工标记已发作为降级路径。

## 7. 用户可见命名与状态规则

### 7.1 用户可见核心状态

用户可见核心状态统一为四个：

```text
待反馈
已反馈
待入档
已入档
```

含义：

| 状态 | 含义 | 触发条件 |
|---|---|---|
| 待反馈 | 已生成可供老师处理的微信反馈，但老师还没有标记已发 | 微信反馈卡片存在，`feedbackStatus = pending_feedback` |
| 已反馈 | 老师已复制/编辑并标记已发 | `feedbackStatus = feedback_sent` |
| 待入档 | 分析结果或反馈结果可沉淀，但尚未确认写入学生档案 | `archiveStatus = pending_archive` |
| 已入档 | 老师已确认写入学生档案 | `archiveStatus = archived` |

### 7.2 状态优先级

反馈状态在入档状态之上。

常规主状态显示优先级：

```text
已反馈 > 待反馈 > 已入档 > 待入档
```

示例：

| feedbackStatus | archiveStatus | 主状态 | 次级状态 |
|---|---|---|---|
| feedback_sent | archived | 已反馈 | 已入档 |
| feedback_sent | pending_archive | 已反馈 | 待入档 |
| pending_feedback | archived | 待反馈 | 已入档 |
| pending_feedback | pending_archive | 待反馈 | 待入档 |
| none | archived | 已入档 | - |
| none | pending_archive | 待入档 | - |

说明：

- 不要把反馈状态和入档状态混成一个数据库字段。
- 数据层应分别保存 `feedbackStatus` 和 `archiveStatus`。
- UI 层根据优先级计算 `displayStatus`。
- 老师日常更关心“有没有给家长反馈”，所以反馈优先于入档展示。
- 入档仍然是长期档案价值的确认动作，但不是状态展示的第一优先级。

### 7.3 异常状态

以下状态不是常规主状态，而是阻断/风险状态：

```text
证据不足
需补充材料
分析失败
```

当报告无法形成可靠反馈或入档候选时，才显示这些状态。

### 7.4 禁止使用的用户可见命名

避免使用：

```text
待老师确认
审核页
evidenceRefs
VisionEvidencePacket
OCR Provider
DeepSeek
Runner
Agent Trace
```

说明：

- 内部字段可以叫 `teacher_review_required`。
- 用户界面不要把页面叫“审核页”。
- 报告状态里“待老师确认”统一改成“待入档”或“待反馈”，取决于当前卡片的主要目的。
- 微信相关卡片优先显示“待反馈 / 已反馈”。
- 档案相关位置显示“待入档 / 已入档”。

## 8. AI 与模型运行规则

当前项目 API 接入 DeepSeek v4 Pro。

DeepSeek v4 Pro 在本项目中只作为文本推理模型使用，不具备多模态图片识别能力。

硬规则：

```text
DeepSeek v4 Pro 不得直接读取图片、PDF、手写、题目区域、bbox 或 crop_ref。
```

图片、PDF、手写答案、老师批改、题目切分、bbox、crop_ref 必须先由外挂 Vision / OCR / Layout 插件识别，并输出结构化：

```text
VisionEvidencePacket
```

DeepSeek v4 Pro 只能消费：

- VisionEvidencePacket。
- 文本题干。
- 学生答案。
- 老师批改。
- 标准答案。
- 评分点。
- 知识点库。
- 学生历史档案。

DeepSeek 输出必须符合：

```text
StudentLearningMaterialAnalysis JSON
```

不得让 DeepSeek 从图片直接生成微信反馈。

## 9. Skill 与卡片规则

正式 AI 输出必须通过 SkillCard 承载。

“正式 AI 输出”包括：

- 学习记录卡片。
- 学情分析卡片。
- 错题分析卡片。
- 微信反馈卡片。
- 月报草稿卡。
- 可入档结论。

非正式聊天回复可以是普通文本，但不能自动入档。

每个 SkillCard 必须包含：

- Skill 名称。
- 输入来源。
- 上下文依据。
- 生成时间。
- 状态。
- 可查看详情入口。
- 可追踪 SkillRun ID。

每个 SkillRun 必须可追踪、可回放、可调试。

## 10. 证据与入档规则

所有学生相关结论必须有证据来源。

必须遵守：

- 不编造课堂事实。
- 不编造学生表现。
- 不承诺提分。
- 不做最终诊断。
- 不根据空白材料推断学生能力。
- 不根据单次材料生成长期标签。
- 不用“基础很差、完全不会、不认真、严重、保证提分”等表达。

入档规则：

```text
AI 只能生成草稿。
老师确认入档后，才形成学生长期档案。
```

反馈状态：

```text
待反馈
已反馈
```

入档状态：

```text
待入档
已入档
```

状态展示规则：

```text
已反馈 > 待反馈 > 已入档 > 待入档
```

也就是说：如果一条分析已经反馈给家长，但还没有入档，主状态仍显示“已反馈”，次级状态显示“待入档”。

所有入档行为必须记录：

- teacherId。
- SkillRun ID。
- source material。
- evidenceRefs 或内部证据引用。
- confirmedAt。
- 写入字段。
- 写入前后版本。

## 11. 学情报告原则

学情报告详情页是反馈型长报告，不是任务计划页。

报告要全面，但表达要面向老师和家长沟通。

报告应该包括：

- 得分或完成情况概览。
- 可追回分或提升空间，若数据不足则不显示。
- 结论总览。
- 数据可信度。
- 提分/学情传导路径。
- 能力维度画像。
- 错误模式聚类。
- 知识薄弱点分析。
- 难度层表现。
- 学习策略表现。
- 学科能力反馈。
- 重点错题成因。
- 优先关注点。
- 复发风险。
- 近期巩固方向。
- 家长微信反馈。
- 反馈状态和入档状态。
- 来源与注意事项。

报告不要包括：

- 每日任务。
- 打卡计划。
- 角色协同行动表。
- 学生/家长任务派发。
- 生成教案。
- 自动承诺分数提升。

## 12. 禁止引入的复杂度

当前阶段不要引入：

- LangGraph。
- Redis。
- 向量库。
- MCP。
- A2A。
- 复杂多 Agent。
- 未经老师最终确认自动发微信，或通过 Hook、模拟点击、个人号托管等非合规方式接管个人微信。
- 自动写入长期档案。
- 自动生成最终诊断。

除非任务明确要求，并且先写明为什么必须引入。

优先使用：

- 内部 API。
- JSON Schema。
- Repository Adapter。
- Mock Adapter。
- Deterministic checks。
- 简单状态机。

## 13. UI 原则

核心 UI：微信式三栏工作台。

- 左侧：学生 / 班级会话列表。
- 中间：聊天流和 SkillCard。
- 右侧：ContextPanel / 分析详情面板。

UI 语言：

- 少按钮。
- 少后台感。
- 少任务化。
- 多反馈。
- 多状态。
- 多来源说明。
- 保持微信式轻量。

学生详情页要安静、清晰、可信。

分析详情页要全面、反馈型、可追溯。

会话页要像老师日常工作入口。

---

## 14. 开发流程

每轮 Codex 任务必须：

1. 先读本文件和 `docs/PRD.md`。
2. 检查现有代码结构，避免重复造模块。
3. 给出简短计划。
4. 小步修改，不做无关重构。
5. 不读取、打印或提交 `.env` / `.env.local` / 密钥。
6. 运行可用的：
   - lint
   - typecheck
   - test
   - build
7. 最后报告：
   - 修改文件。
   - 验证结果。
   - 风险。
   - 下一步。

## 15. Git 安全

如果存在大量未跟踪文件，不要直接：

```bash
git add .
```

必须先运行：

```bash
git status --short
```

并等待用户确认 staging 范围。

不要提交密钥、环境变量、原始学生材料、隐私数据。

## 16. 文档记录

不要写冗长开发日记。

只维护：

```text
docs/codex/task-plan.md
docs/codex/dev-log.md
docs/codex/decision-log.md
```

记录规则：

- `task-plan.md`：当前阶段、任务状态、下一步。
- `dev-log.md`：每个阶段完成后写一次 200-500 字阶段总结。
- `decision-log.md`：只记录长期架构、数据库、AI 行为、权限安全、数据生命周期决策。

不要记录：

- 普通文件创建。
- 琐碎 UI 修改。
- import/export 调整。
- 无长期意义的过程描述。

---

## 17. 数据与安全

必须保护学生材料和老师数据。

禁止：

- 打印学生原始材料。
- 在日志中输出完整 OCR 内容。
- 在前端暴露内部 evidenceRefs 技术字段。
- 把未确认 AI 草稿当正式档案。
- 把学生数据用于测试样例而不脱敏。

必须：

- 原始材料、VisionEvidencePacket、AI 分析草稿、老师确认结果分开存储。
- 所有 profile writeback 记录老师确认行为。
- 删除学生时能处理相关材料、分析、反馈与档案事件。
