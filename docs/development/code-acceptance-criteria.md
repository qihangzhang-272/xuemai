# 学脉代码验收标准

> 版本：V1.0<br>
> 生效日期：2026-08-07<br>
> 适用范围：Web、Mobile、AI / Skill 工作流、服务端接口、数据库变更、测试与缺陷修复

## 1. 验收目标

代码“能够运行”不等于验收通过。一次改动只有在产品行为正确、关键状态完整、数据安全、质量检查通过，并且审核者能依据明确证据复核时，才算完成。

所有代码改动必须同时满足：

1. 做的是 PRD 已定义或本次任务明确授权的内容。
2. 老师能够顺畅完成目标，不需要理解内部实现。
3. 正常、异常、空状态和恢复路径都有明确表现。
4. AI 草稿、老师确认、家长反馈和学生入档之间边界清晰。
5. 不泄露密钥、学生隐私、原始材料和内部技术字段。
6. 相关检查通过，Pull Request 中有可复核的验收证据。

## 2. 必须通过的验收门槛

以下项目均为必检项。任何阻断问题未解决，均不得标记为“验收通过”。

| 验收维度 | 通过标准 | 最低验收证据 |
|---|---|---|
| 需求范围 | 与当前 PRD 和任务目标一致；没有擅自扩大范围、增加新入口或改变既有产品逻辑 | PR 描述需求来源、范围内和范围外内容 |
| 功能结果 | 主流程可完成；保存、编辑、取消、返回、重试等动作结果符合预期 | 验收场景记录；必要时附截图或录屏 |
| 页面状态 | 加载、空数据、成功、失败、无权限、重复操作均有可理解的表现 | 状态清单及验证结果 |
| 老师体验 | 文案是教培老师能理解的业务语言；不要求重复输入系统已有信息；高频路径没有不必要步骤 | 按老师真实工作路径走查 |
| 视觉与交互 | 关键内容层级清晰；按钮含义明确；PC 和移动端在适用范围内可用；没有遮挡、溢出和无法操作的控件 | 页面截图或录屏；响应式走查结果 |
| 状态一致性 | 反馈状态与入档状态分别保存和展示；状态转换可解释；刷新或返回后不丢失正确状态 | 状态转换用例 |
| AI 行为 | 所有学生结论有来源；证据不足时明确提示；AI 只产出草稿；未经老师确认不得自动外发或自动入档 | AI 正常、证据不足和失败用例 |
| 数据与权限 | 不跨老师、机构或学生暴露数据；服务端校验身份与归属；删除、修改和批量操作只影响授权范围 | 权限与隔离用例 |
| 隐私与安全 | 不提交密钥、环境变量、真实学生材料；日志不打印完整 OCR 或隐私数据；前端不展示内部证据字段 | 改动检查和敏感信息扫描结果 |
| 代码质量 | 遵循现有目录、组件和领域模型；命名清晰；无明显重复、死代码、调试输出和无关重构 | 审核者代码检查 |
| 自动化测试 | 新功能覆盖核心行为；修复缺陷包含回归用例；关键分支不能只依赖人工点击 | 测试文件和测试结果 |
| 构建质量 | 所有适用的 lint、类型检查、测试和构建命令成功退出 | PR 中记录实际运行命令及结果 |
| 文档同步 | 产品行为、使用方式、数据结构或协作规则发生变化时，同步更新相应正式文档 | 文档链接或“不适用”说明 |

## 3. 功能验收场景

每项功能至少检查以下适用场景，不得只验证“理想情况下点通一次”。

### 3.1 通用场景

- 正常输入能够完成目标。
- 首次使用或没有数据时，页面有明确空状态和下一步入口。
- 加载期间不会误触、重复提交或显示错误旧数据。
- 输入缺失、格式错误或超出限制时，提示位置和修正方式清楚。
- 请求失败时，用户知道发生了什么，并能重试或安全退出。
- 重复点击、刷新、返回再进入，不会生成重复记录或错误状态。
- 无权限用户看不到或无法操作不属于自己的数据。
- 操作完成后，列表、详情、会话和工作台中的相关状态一致。
- 适用时检查 PC 与移动端，不出现遮挡、横向溢出或不可点击区域。

### 3.2 学脉核心流程

涉及学生学习材料、分析、反馈或入档时，至少验收：

```text
会话记录或上传学生材料
→ 生成 SkillCard
→ 查看分析详情
→ 编辑 / 复制 / 标记已反馈
→ 老师确认入档
→ 学生时间线和相关视图状态更新
```

通过标准：

- 会话是高频操作入口，完整长报告在分析详情页展示。
- 微信反馈卡片包含复制、编辑、标记已发和查看详情。
- 主状态遵循“已反馈 > 待反馈 > 已入档 > 待入档”。
- `feedbackStatus` 与 `archiveStatus` 不被合并成一个状态。
- 老师未确认前，AI 分析不得写成正式学生档案。
- 老师未检查并主动操作前，不得自动向家长发送内容。
- 来源材料不足时显示“证据不足”或“需补充材料”，不得补写不存在的结论。

### 3.3 AI / Skill 场景

涉及 AI 或 Skill 时，除正常结果外必须检查：

- 没有学生作答、批改或练习痕迹的材料。
- 图片模糊、识别不完整或材料相互矛盾。
- AI 输出为空、超时、格式不符合约定或包含风险表达。
- 老师修改 AI 草稿后再复制、发送或入档。
- 同一材料重复发起分析。
- 切换学生、班级或会话后，结果不会串档。

通过标准：

- 不编造课堂事实、学生表现、分数或家长态度。
- 不把单次材料直接变成长期标签。
- 不出现“保证提分”“基础很差”“完全不会”等无依据或不当表达。
- AI 失败不会破坏原始材料和已经确认的数据。
- 正式 AI 输出通过 SkillCard 呈现，来源、时间和状态可追溯。

### 3.4 批量操作场景

涉及批量管理时必须检查：

- 全部成功、部分成功、全部失败和跳过无权限对象。
- 操作前清楚展示对象范围，操作后给出成功、失败和未处理数量。
- 失败项目可以查看原因并重新处理。
- 每个学生的个性化结果独立保留，不被合并覆盖。
- 批量生成不等于批量确认；长期档案不能一键批量确认。
- 未逐项检查的个性化家长反馈不得直接批量发送。

## 4. 数据、权限与安全验收

以下任一情况均为验收阻断：

- 前端传入任意老师、机构或学生 ID 即可读取或修改数据。
- 不同账户之间可以看到对方的学生、材料、分析或反馈。
- 日志、报错或前端页面暴露密钥、完整 OCR、内部证据引用或真实隐私数据。
- 未经老师确认，将 AI 草稿自动写入长期档案。
- 未经老师最终检查，自动向微信或其他外部渠道发送内容。
- 删除学生后，相关材料、分析、反馈和档案事件的处理方式不明确。

涉及数据库结构或数据迁移时，还必须满足：

- 变更目的、影响数据和回退方式明确。
- 已有数据有兼容或迁移方案。
- 必填、唯一、关联和权限规则与业务一致。
- 不使用真实学生数据作为测试样例，测试数据必须脱敏或虚构。

## 5. 自动化检查标准

### 5.1 Web / 服务端 / AI 工作流改动

在仓库根目录运行：

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

### 5.2 Mobile 改动

除根目录适用检查外，在 `mobile/` 目录运行：

```bash
npm run lint
npm run typecheck
```

### 5.3 纯文档改动

至少完成：

- 检查新增和修改的文档链接可以定位到实际文件。
- 检查 Markdown 标题、表格和代码块格式。
- 运行 `git diff --check`，确保没有空白错误。

通过标准：所有适用命令退出码为 `0`。如果因外部环境无法执行，必须在 PR 中写明未执行项、原因和风险，不能直接宣称验收通过。

## 6. 缺陷分级与验收结论

### 6.1 阻断问题

出现以下任一问题，验收结论必须为“不通过”：

- 实现与需求目标不符，或核心流程无法完成。
- 页面崩溃、数据丢失、串档、重复写入或错误覆盖。
- 越权访问、隐私泄露、密钥泄露或高风险安全问题。
- AI 无依据生成学生结论，或未经确认自动发送、自动入档。
- 关键异常状态没有处理，用户无法恢复。
- 适用的 lint、类型检查、测试或构建失败。
- 新增核心行为没有可复核的测试或验收证据。

### 6.2 非阻断问题

不影响任务完成、数据正确性和安全性的轻微视觉或文案问题，可在审核者明确同意后记录为后续事项。但必须写清影响范围和处理计划，不能用“以后再优化”代替判断。

### 6.3 最终结论

验收只使用以下结论：

```text
通过
有条件通过
不通过
```

- **通过**：无阻断问题，所有适用门槛和检查均通过。
- **有条件通过**：无阻断问题，仅存在审核者已接受并记录的非阻断事项。
- **不通过**：存在任一阻断问题，或验收证据不足以确认结果。

## 7. Definition of Done

一项代码任务只有同时满足以下条件才算完成：

- [ ] 已实现本次授权范围内的全部行为。
- [ ] 已按老师真实工作路径完成主流程走查。
- [ ] 已检查适用的空、错、慢、无权限、重复操作和恢复场景。
- [ ] 已验证反馈、入档及其他关联视图的状态一致性。
- [ ] AI、隐私、权限和数据边界符合项目规则。
- [ ] 新功能或缺陷修复有相应自动化测试。
- [ ] 所有适用质量检查通过。
- [ ] 没有混入无关重构、个人文件、真实学生材料或环境变量。
- [ ] 相关正式文档已同步，或已明确说明不需要更新。
- [ ] Pull Request 已提供审核者可以复核的验收证据。
- [ ] 审核意见已处理，满足合入条件。

## 8. Pull Request 验收证据格式

每个代码类 Pull Request 至少写清：

1. **目标**：这次解决老师的什么问题。
2. **范围**：做了什么，明确没有做什么。
3. **验收场景**：正常场景和关键异常场景分别如何验证。
4. **状态与数据影响**：涉及哪些页面、状态、角色和已有数据。
5. **检查结果**：实际运行了哪些命令，结果如何。
6. **视觉证据**：涉及界面时提供关键页面截图或录屏。
7. **风险与降级**：仍有哪些限制，失败时如何恢复或回退。

审核者应能只依据 Pull Request、对应需求和测试结果，判断这次改动是否可以安全合入。
