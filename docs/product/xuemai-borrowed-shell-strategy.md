# 学脉借壳路线评估与执行计划

日期：2026-06-30  
文档性质：产品策略评估，不是正式 PRD  
目标：判断学脉是否可以借用成熟软件架构，降低从零开发成本，并给出可执行路线

---

## 1. 结论

学脉可以走借壳路线，但不能走盗版扒壳或纯换皮路线。

推荐方向：

```text
教培 CRM / 课时管理壳
+ 学脉自己的 AI SkillCard 内核
+ 老师确认入档机制
+ 学生长期档案和月报复用
```

也就是：

- 借成熟软件的信息架构、页面组织、基础数据模型。
- 不复制闭源软件代码、素材、商标和专有交互。
- 不把学脉做成普通教务后台。
- 不把 AI 只做成一个“生成反馈”按钮。

当前最稳妥路线不是直接基于 Moodle、Odoo、ERPNext 这类大型系统二开，而是参考它们的模块边界，继续在当前 Next.js 工作台里做一个轻量教培 CRM 壳，把学脉核心 AI 工作流嵌进去。

---

## 2. 外部案例观察

### 2.1 白标 SaaS：GoHighLevel SaaS Mode

来源：<https://www.gohighlevel.com/saas-mode>

GoHighLevel 的 SaaS Mode 本质不是简单换 logo，而是把代理商服务产品化。它强调：

- 客户侧功能：双向短信、网页聊天、Messenger、声誉管理、未接来电自动短信等。
- 代理商侧功能：自动子账号生成、自动用户和权限生成、欠费锁定、Twilio 转售、SaaS Dashboard。
- 变现侧功能：连接 Stripe、配置套餐、定价、试用期、自动开通。

对学脉的启发：

- 真正有价值的“套壳”不是 UI 换皮，而是多租户、权限、套餐、状态、开通流程。
- 学脉早期可以不做计费，但数据结构要预留 teacher / organization / workspace。
- 机构版以后需要子账号、老师权限、学生归属、机构空间，而不是临时加字段。

不适合直接照搬：

- GoHighLevel 是营销自动化和 SMB CRM，不是教学服务系统。
- 它的短信、营销漏斗、广告获客功能对学脉 MVP 是干扰项。

### 2.2 白标平台：Vendasta

来源：<https://www.vendasta.com/platform/>

Vendasta 把获客、销售、账单、交付、客户门户、项目管理、Marketplace 组合成代理商平台。它强调“一套平台完成销售、计费、交付”，并提供 white-label 交付团队和客户沟通。

对学脉的启发：

- 一个垂直 SaaS 的价值不是某个单点工具，而是把重复服务流程产品化。
- 学脉也应该把“课后服务交付”产品化：记录、分析、反馈、标记已发、入档、月报、续费证据。
- 后期可以把“机构老师服务家长”的过程做成一个可追踪交付流程。

不适合直接照搬：

- Vendasta 面向数字营销代理商，功能过宽。
- Marketplace、外包交付、客户营销自动化都不是学脉第一阶段需要的东西。

### 2.3 模块化 ERP / CRM：Odoo

来源：<https://www.odoo.com/page/editions>

Odoo 官方把产品分成 Community 开源版和 Enterprise 授权版，模块覆盖 CRM、销售、订阅、网站、eLearning、项目、Timesheet、Planning、Appointment、Discuss、Calendar 等。

对学脉的启发：

- 模块化是可以借鉴的：学生、班级、课时、日历、反馈、月报、设置应该是清晰模块。
- App 式模块边界有利于后期从个体老师版扩展到机构版。
- 但 MVP 不能上来就做全套 ERP。

不适合直接作为底座：

- Odoo 过重，字段、权限、会计、库存、销售等上下文会污染学脉。
- 如果直接在 Odoo 上改教学 AI 工作台，核心体验会被 ERP 后台气质拖住。

### 2.4 教育 ERP：ERPNext / Frappe Education

来源：

- <https://erpnext.com/education>
- <https://frappe.io/education>

ERPNext / Frappe Education 覆盖招生、学生记录、费用、课程、班级、评估、学习结果、权限等。Frappe Education 明确是面向 academic institutes 的开源 ERP 方案。

对学脉的启发：

- 学生记录、班级、课程、收费、评估这些实体可以参考。
- 费用和课时流水可以作为后期机构版能力。
- 角色权限、审批流、报表是机构版需要提前想清楚的能力。

不适合直接作为第一版底座：

- 它们更像学校 / 学院 / 机构管理系统，不是个体教培老师的轻工作台。
- 学脉核心是微信式课后服务，不是招生、学籍、收费、成绩管理大系统。

### 2.5 LMS：Moodle / OpenOLAT / ILIAS

来源：<https://en.wikipedia.org/wiki/Moodle>

Moodle 这类 LMS 适合课程内容、作业、测验、学习平台和插件生态。它们证明开源教育软件可以长期运行，也说明教育领域很容易做重。

对学脉的启发：

- 插件、主题、角色权限、课程活动可以借鉴。
- 如果后期做“练习派发 / 作业系统 / 学生端”，LMS 模型有参考价值。

不适合当前路线：

- 学脉不是学生自学平台，也不是在线课程平台。
- 现在不应做课程内容管理、在线学习、学生端任务中心。

### 2.6 低代码 / 内部工具壳：Appsmith

来源：<https://www.appsmith.com/>

Appsmith 强调快速连接数据库、SaaS、REST / GraphQL API，通过拖拽组件和 JS 定制构建内部应用，并支持自托管、Git 集成和开源社区版。

对学脉的启发：

- 内部运营后台可以用低代码思路，不必全部手写。
- 管理 teacher / student / skill_run / feedback / archive_event 这类后台数据时，可以借内部工具形态。

不适合做老师端主产品：

- 老师端体验需要像微信和轻 CRM，不能像内部管理后台。
- 低代码适合后台，不适合做学脉核心差异体验。

## 3. 候选路线对比

| 路线 | 成本 | 上线速度 | 可控性 | 学脉匹配度 | 风险 | 判断 |
|---|---:|---:|---:|---:|---|---|
| 直接买白标 SaaS 改品牌 | 低到中 | 快 | 低 | 中 | 锁定、隐私、定制受限、国内合规和微信场景不稳 | 不作为主线 |
| 找开源教务 / ERP 系统二开 | 中 | 中 | 中 | 中 | 系统过重，改造成本可能反超自研 | 只做技术备选 |
| 复刻成熟教培 CRM 信息架构，自研核心 | 中低 | 中快 | 高 | 高 | 需要产品取舍清楚 | 推荐主线 |
| 用低代码搭后台 + 自研老师端 | 中低 | 快 | 中高 | 高 | 后台和前台割裂 | 推荐辅助 |
| 完全从零设计学脉 | 高 | 慢 | 高 | 高 | 产品摸索成本高 | 不推荐当前阶段 |

推荐组合：

```text
前台老师端：自研轻量教培 CRM / 微信式工作台
后台管理端：可参考低代码 / 表格型后台
产品结构：参考课时管理系统 + CRM + 白标 SaaS
AI 内核：学脉自研 SkillCard / SkillRun / ArchiveEvent
```

## 4. 学脉可以借什么

### 4.1 可以直接借鉴的信息架构

| 借鉴对象 | 可借内容 | 学脉落点 |
|---|---|---|
| 教培课时管理系统 | 今日课程、排课、消课、班课点名、课后反馈入口 | 工作台 / 课时 / 班级 |
| CRM | 联系人、标签、状态、时间线、跟进记录 | 学生 / 家长沟通 / 续费跟进 |
| 白标 SaaS | workspace、角色、权限、套餐、子账号、设置 | 机构版预留 |
| ERP / Education ERP | 学生记录、课程、班级、费用、权限 | 数据模型参考 |
| LMS | 课程、作业、测验、插件 | 后期学生端或练习系统参考 |
| 低代码后台 | 数据表管理、审核、日志、运营看板 | 内部管理后台 |

### 4.2 可以删掉的常见功能

第一版不要做：

- 在线支付闭环。
- 家长端完整 App。
- 学生端学习平台。
- 课程内容管理。
- 招生 CRM。
- 多校区、多层级组织架构。
- 复杂财务报表。
- 营销自动化。
- 自动发微信。
- 自动最终诊断。

### 4.3 必须自己保留的学脉核心

这些不能外包给壳：

- SkillCard。
- SkillRun 追踪。
- 微信反馈卡。
- 反馈状态：待反馈 / 已反馈。
- 入档状态：待入档 / 已入档。
- 老师确认入档。
- 学生学习材料分析。
- 证据来源和可信度。
- 学生时间线。
- 月报素材复用。
- AI 不能绕过老师确认。

如果借来的系统无法承载这些状态，就只能当参考，不能当底座。

## 5. 推荐产品形态

### 5.1 定位

```text
学脉 = 面向个体教培老师和小机构的 AI 课后服务 CRM
```

不是：

```text
完整教务系统
在线学习平台
大型机构 ERP
ChatGPT 套壳
```

### 5.2 第一版页面

| 页面 | 借壳来源 | 页面职责 |
|---|---|---|
| 工作台 | 课时管理 / CRM 首页 | 看今天课程、待反馈、待入档、最近学生 |
| 学生 | CRM 联系人 | 学生列表、学生详情、标签、状态 |
| 班级 | 群组 / 班课管理 | 班级列表、班课记录、批量反馈 |
| 课时 | 教培管理系统 | 排课、上课记录、消课状态 |
| 反馈 | CRM 待办 / 工单 | 集中处理待反馈、已反馈 |
| 分析详情 | 学脉自研 | 完整报告、证据、微信反馈、入档 |
| 设置 | 白标 SaaS | 老师偏好、机构信息、账号、反馈风格 |

### 5.3 第一版主闭环

```text
创建学生
→ 创建课程 / 课堂记录
→ 生成学习记录 SkillCard
→ 老师确认入档
→ 生成微信反馈 SkillCard
→ 复制 / 编辑 / 标记已发
→ 反馈状态变为已反馈
→ 老师确认入档
→ 学生时间线沉淀
→ 月报读取这些记录
```

## 6. 执行计划

### 阶段 0：借壳对象筛选，1-2 天

目标：找 5-8 个可参考对象，不追求直接拿来用。

输出：

- 候选系统清单。
- 页面截图 / 视频观察笔记。
- 模块拆解表。
- 许可证和商用风险初筛。

筛选标准：

- 是否有学生 / 班级 / 课时 / 反馈 / 时间线。
- 是否支持多账号和权限。
- 是否能自托管或合法二开。
- 是否过重。
- 是否适合中国教培老师日常微信工作流。

### 阶段 1：壳结构定稿，2-3 天

目标：冻结学脉第一版不从零设计的页面结构。

输出：

- 学脉低成本壳结构图。
- 页面清单。
- 功能删减清单。
- 数据实体映射。

建议冻结结构：

```text
工作台 / 学生 / 班级 / 课时 / 反馈 / 设置
```

其中聊天不是唯一入口，而是学生或班级里的高频记录入口。

### 阶段 2：数据模型对齐，2-4 天

目标：把借壳页面和学脉核心状态打通。

核心实体：

- teacher
- organization
- student
- class
- lesson
- conversation_thread
- conversation_message
- skill_run
- skill_card
- feedback
- archive_event
- monthly_report_material

重点：

- feedbackStatus 和 archiveStatus 分开。
- SkillRun 必须可追踪。
- ArchiveEvent 记录老师确认动作。
- 学生时间线只显示确认后的长期信息，AI 草稿不能直接入档。

### 阶段 3：前端壳改造，1-2 周

目标：在当前工作台基础上完成“教培 CRM 壳”。

优先顺序：

1. 工作台：今日课程、待反馈、待入档。
2. 学生：联系人列表、详情、时间线。
3. 反馈：待反馈 / 已反馈集中处理。
4. 分析详情：承载完整报告。
5. 设置：反馈风格和老师信息。

暂不做：

- 家长端完整门户。
- 支付。
- 多校区权限。
- 学生端任务。

### 阶段 4：AI 内核接入，1-2 周

目标：把壳和学脉核心能力连起来。

优先接：

1. 课堂记录整理。
2. 微信反馈生成。
3. 标记已发。
4. 确认入档。
5. 学生时间线更新。
6. 月报素材读取。

不做复杂 Agent：

- 先 workflow。
- 先 mock / deterministic fallback。
- 再接真实 AI。

### 阶段 5：上线预览，3-5 天

目标：让真实老师能试用一条完整链路。

验收：

- 老师能创建学生。
- 能记录一次课。
- 能生成反馈。
- 能复制并标记已发。
- 能确认入档。
- 学生时间线能看到结果。
- 月报草稿能读取记录。

## 7. 决策门槛

只有满足下面条件，才进入具体开发：

1. 借壳对象不涉及侵权复制。
2. 页面结构不破坏学脉 SkillCard 和入档机制。
3. 第一版能在 2-4 周内跑通核心闭环。
4. 不需要引入重型 ERP / LMS 底座。
5. 数据模型可以支持后期机构版。
6. 老师端体验仍然轻，不变成后台管理系统。

如果某个候选系统要求我们改掉学脉核心逻辑，就放弃它。

---

## 8. 风险与边界

### 法务风险

- 不复制闭源系统代码。
- 不使用未授权素材、图标、商标、文案。
- 开源项目必须确认许可证，尤其是 AGPL / GPL 对 SaaS 和二开的影响。

### 数据风险

- 不把真实学生材料传到不可信第三方。
- 不在日志里打印学生原始材料。
- AI 草稿和老师确认后的档案必须分开存。

### 产品风险

- 借壳过度会变成普通教务系统。
- 功能删得不够会拖慢上线。
- 太依赖某个开源 ERP 会导致改造成本失控。
- 老师日常最关心的是反馈和复用，不是后台字段完整。

## 9. 下一步建议

当前已新增一个隔离原型路由：

```text
/borrowed-shell
```

该原型用于验证“教培 CRM / 课时管理壳 + 学脉 AI 反馈内核”的组合，不替换现有首页和 `/workbench-v2`。

后续不要马上选重型技术底座，先做一张候选系统评估表。

建议评估对象：

1. 当前已还原的 LessonLedger 课时管理系统。
2. GoHighLevel SaaS Mode。
3. Vendasta。
4. Odoo。
5. ERPNext / Frappe Education。
6. Moodle。
7. Appsmith。
8. 一个国内教培课时管理竞品。

评估维度：

- 是否能借页面结构。
- 是否能借数据模型。
- 是否适合个体老师。
- 是否能承载 AI 反馈闭环。
- 是否能合法二开。
- 是否过重。
- 是否有上线速度优势。

阶段性推荐：

```text
主参考：LessonLedger 类教培课时管理系统
辅助参考：CRM 时间线 + 白标 SaaS 权限/套餐
不直接采用：Odoo / ERPNext / Moodle 作为第一版底座
内部后台参考：Appsmith 类低代码工具
```
