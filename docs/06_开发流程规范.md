# 开发流程规范

## 推进原则

- 一次只做一个小阶段。
- 当前阶段未验收，不进入下一阶段。
- 不擅自扩展产品范围。
- 优先保证稳定、安全、可理解，再追求功能完整。

## 每次开发前

Codex 必须先说明：

1. 这次要改哪些文件或目录。
2. 为什么要改。
3. 完成后如何运行和验收。

如果需求不明确，先沟通需求，不直接写代码。

## 每次开发中

- 遵守 `docs/01_产品范围说明.md` 的范围边界。
- 遵守 `docs/03_技术规范.md` 的技术和安全规则。
- 遵守 `docs/04_设计规范.md` 的 UI 风格要求。
- 不把业务逻辑全部堆在 `page.tsx`。
- mock data 放在 `lib/mock/`。
- 不在前端暴露密钥。

## 每次开发后

优先运行：

```bash
npm run lint
npm run typecheck
npm run build
```

然后按信息价值决定是否更新 `docs/codex/`：

- `docs/codex/task-plan.md`：当前 Phase、任务状态、下一步计划。
- `docs/codex/dev-log.md`：每完成一个 Phase 后写一次阶段总结，控制在 200-500 字以内。
- `docs/codex/decision-log.md`：只记录影响长期架构、数据库设计、Agent 行为、Harness 分层、权限安全、数据生命周期的关键决策。

## 记录规则

- 不写流水账。
- 不写长篇开发日记。
- 每个 Phase 最多写一次 `dev-log.md`。
- 普通文件创建、按钮样式、琐碎 bug 修复、import/export 调整和无长期影响的 UI 微调不进入长期记录。
- 文档是为了帮助后续 Codex 接续开发，不是为了记录所有操作过程。

## 阶段验收

- Phase 1：所有 mock 页面可访问，UI 不明显崩坏，构建通过。
- Phase 2：Supabase Auth、数据库 schema、RLS 可用，未接 AI。
- Phase 3：班级与学生真实 CRUD 可用。
- Phase 4：练习记录保存和单次微信反馈生成可用。
- Phase 5：错题分析和训练建议可用。
- Phase 6：月度总结可用。
- Phase 7：学生洞察可用。
- Phase 8：Vercel 部署和试用准备完成。
